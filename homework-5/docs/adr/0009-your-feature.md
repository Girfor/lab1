# ADR 0009 — Переименование Passes в AccessPasses без остановки сервиса

- **Статус:** Accepted for educational implementation
- **Дата:** 2026-10-31
- **Связанная задача:** CAMPUS-101
- **Сервис:** Smart Campus, турникеты и пропускной режим

## Контекст

Таблица `Passes` используется действующим сервисом пропусков. Прямое
`ALTER TABLE ... RENAME TO "AccessPasses"` одномоментно меняет контракт SQL:
экземпляры старой версии начинают получать ошибку отсутствующей таблицы.
В PostgreSQL DDL также получает блокировки. Необходимо поддержать смешанное
развёртывание старых и новых клиентов и перенести все исторические записи.

## Решение

Использовать **Expand and Contract** с явными фазами:

1. **Expand:** создать `AccessPasses` со совместимой схемой. На `Passes`
   установить `AFTER INSERT/UPDATE/DELETE` триггер, который зеркалирует
   действия старых клиентов в новой структуре в той же транзакции.
2. **Dual-write:** v1.9.0 в режиме `CAMPUS_SCHEMA_MODE=dual` пишет в обе
   таблицы внутри одной транзакции PostgreSQL, а читает из `Passes`.
   Параллельно `02_migrate.sql` догружает историю пакетами и блокирует только
   переносимые строки с помощью `FOR UPDATE SKIP LOCKED`.
3. **Cutover:** после сверки и вывода старых экземпляров переключить сервис
   на `CAMPUS_SCHEMA_MODE=new`: чтение/запись только `AccessPasses`.
4. **Contract:** в отдельном одобренном релизном действии удалить триггер,
   функцию и `Passes`, только если все исторические ID есть в новой таблице.

`id` (UUID) сохраняется. Теги текущей `Activity` — `jira.issue=CAMPUS-101`
и `campus.pass_id=<UUID>`. Идентификатор пропуска нужен для связывания логов,
запросов и карточки изменения; персональные данные в тегах не используются.

## Альтернативы

| Альтернатива | Почему отклонена |
| --- | --- |
| Мгновенный `ALTER TABLE RENAME` | Старые экземпляры обращаются к `Passes` и ломаются |
| Полная остановка на время миграции | Пропускной режим должен оставаться доступным |
| Только dual-write в C# без триггера | Старые бинарники не знают о новой таблице |
| VIEW `Passes` поверх новой таблицы | Нужно отдельно тестировать поддержку INSERT/UPDATE/DELETE, триггеров и клиентских прав |

## Последствия и эксплуатация

**Плюсы:** прежний контракт сохранён на переходном этапе; история мигрирует
постепенно; можно откатить приложение до удаления старой таблицы.

**Минусы:** временно удваиваются записи, объём хранения и вероятность ошибок
на интеграционных границах. Требуется контроль схемы, write-path, блокировок
и метрик. Записи, внесённые только в новую таблицу после cutover, допустимы,
поэтому контрактная сверка гарантирует наличие **всех старых строк в новой**,
а не равное число строк в обеих таблицах.

**Откат:** `kubectl rollout undo` безопасен до Contract; после удаления
`Passes` нужен совместимый forward-fix или восстановление резервной копии.

**Ограничение:** пример построен на минимальной учебной схеме из
`sql/00_demo_schema.sql`. При переносе на реальную ИС потребуется
инвентаризация внешних ключей, индексов, представлений, GRANT, CDC,
отчётов и всех SQL-запросов, а также проверка способа синхронизации для
каждой дополнительной операции.

## Проверка принятого решения

- CI: `build-and-test` + `sql-migration-check`.
- После backfill: сравнение полей всех legacy строк с новыми.
- После deploy: `ProductionSanityTests` создаёт пропуск с `is_test=true`,
  читает его и удаляет в `finally`, затем проверяет 404.
- Перед Contract: отдельно проверить отсутствие старых экземпляров/клиентов.
