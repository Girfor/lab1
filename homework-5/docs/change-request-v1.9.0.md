## Описание и бизнес-цель

В сервисе пропусков на турникетах название `Passes` неоднозначно и не отражает
назначение сущности. Название `AccessPasses` делает модель понятнее для
поддержки и интеграций. Функциональное поведение и идентификаторы пропусков
сохраняются. Обязательное условие: старые клиенты продолжают работать во время
миграции, исторические записи не теряются.

## Окно обслуживания

**Предлагается:** воскресенье, **1 ноября 2026 г., 02:00–03:00 МСК (UTC+3)**.
Для учебной ИС предполагается, что ночной поток входов ниже, чем между
08:00–18:00 в учебный день. Это гипотеза: перед реальным релизом необходимо
сравнить почасовую телеметрию турникетов за последние четыре недели и при
необходимости изменить окно. При критичном росте ошибок или задержек релиз
останавливается даже внутри окна.

5. Дежурный инженер наблюдает 5xx, p95 API, ошибки синхронизации и здоровье

## План выполнения

| Этап | Действие | Критерий перехода |
| --- | --- | --- |
| 0 | Backup БД, проверка CI, базовые метрики | Backup доступен, алерты активны |
| 1 Expand | `01_expand.sql`: новая таблица + триггер совместимости | Таблица создана; старые записи/обновления проходят |
| 2 Deploy | Развернуть v1.9.0 с `CAMPUS_SCHEMA_MODE=dual` | `/health/live` = 200, нет всплеска 5xx |
| 3 Migrate | `02_migrate.sql`: перенос маленькими пакетами | Нет отсутствующих и расходящихся строк |
| 4 Sanity | xUnit-тест создать → прочитать → удалить тестовый пропуск | POST 201, GET 200, DELETE 204, GET 404 |
| 5 Observe | Мониторинг ошибок и записей, выдержка наблюдения | Ошибки в пределах базовых значений |
| 6 Cutover | После отключения старых клиентов развернуть `CAMPUS_SCHEMA_MODE=new` | Чтение и запись работают только с `AccessPasses` |
| 7 Contract | **Отдельное согласование:** `03_contract.sql` после наблюдения и backup | Нет старых клиентов, данные сверены, CR одобрен |

Обслуживание не означает обязательную остановку API. DDL в PostgreSQL всё же
может кратковременно брать блокировки; установлен `lock_timeout = '3s'`, а при
конфликте шаг повторяется после диагностики, не удерживая очередь запросов.

## План отката и точки остановки

- **До Contract:** остановить изменение, выполнить
  `kubectl rollout undo deployment/campus-access-control -n campus-prod`.
  Таблица `Passes` ещё существует; триггер остаётся. Проверить `rollout status`,
  здоровье API и чтение существующего пропуска. Не удалять `AccessPasses`
  немедленно: сначала разобраться в изменённых данных.
- **При сбое backfill:** завершить или повторить `02_migrate.sql` после
  диагностики; работа старого API не требует удаления новой таблицы.
- **После Contract:** откат старого бинарника **запрещён**, так как он обращается
  к удалённой `Passes`. Использовать совместимый hotfix/forward-fix либо
  восстановление из проверенного backup по отдельной аварийной процедуре.

## Риски и меры снижения

| Риск | Мера |
| --- | --- |
| Старые экземпляры пишут только в `Passes` | Триггер до окончания cutover |
| Расхождения или потеря обновлений | Запись в транзакции, пакетные row locks, SQL-сверка |
| Блокировка на DDL | Короткий `lock_timeout`, off-peak окно, повтор после диагностики |
| Ошибки в продакшн-тесте | Только `is_test`, удаление в `finally` и повторная проверка GET 404 |
| Преждевременный DROP | Ручной guard `campus.contract_approved=yes` и отдельное одобрение |
